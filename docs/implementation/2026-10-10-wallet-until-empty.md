# 按可用余额使用到耗尽

## 问题与实际状态

开发版账号余额与可用余额均为 348.10096 Credits，预留余额 0，无活动模型请求。此前的预留算法仍要求保守输入估计及至少 256 个输出 token 全额可支付，因此历史影像任务在余额为正时被拒绝。UTF-8 字节估计远高于供应商实际 token，不能作为钱包准入门槛。

## 新规则

- 托管模型只在可用余额为零时拒绝新请求。任意正可用余额均可发起请求。
- 不再按钱包余额降低供应商 `max_tokens`；保留模型正常配置的输出容量。用户主动配置的模型容量、任务权限和无效重复保护仍按原合同执行。
- SQLite 事务中仅预留估计费用与可用余额的较小值，防止并发请求重复使用同一份钱。尚未核对的请求继续持有预留；余额被占用与余额已耗尽使用不同错误码。
- 用供应商可信回执和发起时价格快照计费。实际扣费最多为当时可用的钱包资金，排除其他未结束请求的预留。余额不为负，最后一笔可以扣到零；超出的本次费用记录为减免，不形成未来充值的欠款。
- 报价、实际扣费和减免分别留档：`quotedNanoCny`、`chargeNanoCny`、`waivedNanoCny`。完整 token 用量及价格快照保留，重放和重启不会重复扣费。
- 新预留通过 `requestBounds.billingPolicy=wallet-until-empty-v1` 标识；历史预留保留原合同，不改写历史扣费、赠额和待核对记录。无数据库结构迁移。
- 服务器证明请求因余额问题在调用模型前已失败，且本机执行已空闲时，客户端自动解除该请求的待核对锁定。无法获取证据、执行仍活跃、用量未知或其他错误继续保留恢复流程，不自动重发任务。

## 验证

- 本地网关 101 项标准回归通过；客户端恢复流程 7 项测试通过；前端生产构建和原生开发构建通过。
- 针对 348.10096 Credits 的大输入请求、极小正余额、正常输出长度、连续 18 次请求至余额归零、并发占用、最后一次扣费封顶、重放及重启测试通过。
- 测试使用确定性供应商和隔离账本，未发起额外付费模型调用。
