# 有余额却无法发起模型请求

## 实际原因

开发版原生接口读取的托管模型为 `deepseek-flash`，服务器上下文容量 128,000、最大输出 8,192。余额及可用余额均为 580.37184 Credits，无预留余额、无活动 AI 请求。

旧服务器按整个上下文容量预留输入费：

```text
128000 × 4000 + 8192 × 16000 = 643072000 nano-CNY
                            = 643.072 Credits
```

因此新会话中只发“你好”也被拦截。这次拦截发生在调用供应商前，不扣费。线上当前版本已通过只读检查确认存在该逻辑。

## 修复

- 网关只对实际提交给供应商的规范化消息、指令和工具契约估算输入，不把上下文容量当作本次实际用量。文本采用 UTF-8 字节数加协议余量的保守估计；上下文容量只是上界。图片 token 成本暂保留上下文上界，不能把图片 URL 长度等同图片 token。
- 在同一个 SQLite 事务内读取可用余额、已有预留，计算可以覆盖的最大输出并冻结相应费用。余额不足以覆盖输入与至少 256 个输出 token 时才拒绝。
- 余额不能覆盖配置的完整最大输出时，降低这次供应商请求的 `max_tokens`；不能只少预留费用却仍放行无限输出。正常余额继续使用原输出上限。
- 输出和输入预算保存在原有不可变价格快照的 `requestBounds` 中；重放原预留返回原预算，客户端传入的金额及输出上限不作为可信费用。
- 最终按供应商实际用量、原有价格快照结算，释放差额。丢失响应或无法确认用量仍保留待核对预留；超出可信预留的用量保留复核状态，不部分扣账。
- 不调整价格、不补发额度、不修改历史扣费或既有预留，无数据库表结构迁移。

## 验证

本地网关全部 97 项回归通过。新增实际 HTTP 用例覆盖：

1. 580.37184 Credits 在一百万 token 上下文容量下仍可通过 Codex 流式接口发出“你好”、收到中文回复并正常结算，释放预留。
2. 50 Credits 请求会同时降低真实上游输出长度与预留金额；伪造的客户端金额、超大输出配置不能改变服务器预算。丢失响应的预留跨重启保留。
3. 实际输入已不可支付时，模型不被调用；两个并发请求竞争低余额时只有一个派发，钱包不超支。

这些测试使用本地确定性供应商，未消耗用户额度，不能代表付费模型的实际回复质量或平均费用。

线上源文件已只读下载至 `artifacts/credit-reservation-20261010/production-source`。基于原线上 `server.mjs` 单独制作余额修复，仅替换三个模型网关文件，保留该版本的指令、工具契约和其他功能。补丁的相同 16 项余额/赠额测试通过。
