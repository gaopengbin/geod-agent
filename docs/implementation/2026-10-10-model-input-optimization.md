# GeoD Agent 按需加载模型输入

## 实际问题

实际问候请求的模型回执：输入 20,558 tokens（其中缓存命中 3,328），输出 38 tokens，总计 20,596。不是问候文字本身产生这么多输入。

检查本机 Codex 原始会话记录发现：

- 73 个 GeoD 动态工具的完整定义，序列化后 50,152 bytes。
- developer 说明共 23,366 字符。其中 GeoD 产品说明约 12,827 字符，Core 附加技能说明约 6,600 字符，权限说明约 3,939 字符。
- 此会话没有大量既有任务历史。问候文字包含语言前缀后只有 43 字符。

工具定义和规则都会成为模型输入；缓存 token 是输入 token 的子集。网关没有保存完整原始请求，因此不能从账单给每类输入分配精确的 token 数。上述各类体积来自原始 Core 记录，不是 tokenizer 估算。

## 运行层修改

新增 `model-input-context.mjs`，在模型供应商请求边界投影输入，保留 Codex 0.159.2 的执行核心和完整持久化线程。

1. 全部工具仍向 Core 注册。常见影像、图源、地图、附件、数据库、连接器、定时和缓存请求自动带上相关工具的完整参数定义。
2. 其他工具通过只读 `runtime_tools_search` 发现；发现结果启用下一次模型请求中的准确 schema。目录支持分页，不丢失任何工具。工具结果仅返回名称和短说明，避免再次向历史复制整套 schema。
3. 仅明确的问候或致谢使用精简输入。确认、继续、带任务的问候、后台执行、附件、图片和已选技能不会进入此路径。正在问候时收到新的行动指令会立即恢复任务输入。
4. 正常任务保留完整对话历史、已有工具调用与结果、已确认参数、坐标系与澄清规则、权限说明及 Core 的内置工具。Core 自己发起的上下文总结请求保留完整来源，防止压缩时丢失任务状态。
5. 搜索同样经过现有运行层只读权限门禁；原生执行授权和工具参数检查继续生效。
6. 新增 `model-input-audit.jsonl` 元数据：原始/发送字节数、工具数量、输入类型、选中组和请求标识。不记录原始提示词、凭证或私有正文。

这次没有降低正常任务的上下文上限或输出上限，也没有修改线上服务。
