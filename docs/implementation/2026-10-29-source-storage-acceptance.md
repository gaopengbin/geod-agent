# 2026-10-29：Agent 分盘空间检查与下载诊断

本轮是本地修复与验证，没有发布新安装包、重启用户的正式客户端或修改生产网关。客户原设备上的任务未复现，不能计为已交付。

## 反馈归属

- **旧 GeoDownloader 3.6.14 / 3.6.20**：内置高德卫星叠加手动卫星注记，成果 E 盘、缓存 D 盘，报 `TILE_ACCESS_DENIED / HTTP 403`。两个版本的下载器源码已只读核对。当前本机内置卫星单瓦片请求返回 200；带旧版通用 Google Referer 与不带该头的对照均为 200、内容摘要相同，不能把该头判为此次 403 的已证实原因。手动注记 URL、客户网络和实际被拒绝的图层仍未知；**旧产品 403 未定位、未修复、未宣称通过**。旧仓库的在途改动未修改。
- **GeoD Agent 0.2.14**：图源由 Agent 添加，成果 E 盘、缓存 C 盘，用户反馈保存盘有 600 多 GB 但提示空间不足。客户 C 盘可用空间、E 盘文件系统、实际保存的图源模板和任务诊断未取得，**不能认定客户机器只是误报，也不能用本机数据代替客户数据**。

## 已确认并修复

1. 原实现将成果、临时文件和双份缓存的完整预算分别用于保存目录与缓存目录检查。现在按实际写入用途拆分，按真实文件系统归组；同盘累计检查，分盘各查所需空间。Windows 使用实际卷标识，包含路径重定向和挂载点，不只比较盘符。
2. 40,200 张 256 px 瓦片、单输出的原总预算为 43,486,806,016 bytes。同盘仍检查该总量；分盘时成果/临时目录约 21.09 GB，缓存目录约 22.41 GB（各自保留余量）。这是保守预算，不是最终压缩文件大小。测试中的“600 GB 保存盘 + 30 GB 缓存盘”通过，真实不足的缓存盘仍会阻止执行并明确标记。
3. 失败时保存本地结构化诊断：两处真实目录、各卷所需/可用字节及检查结果。旧事件不补造空间数据。界面明确是失败时的快照，提供现有缓存管理入口；重试原任务会重新检查，沿用原任务与审批。
4. 通用 HTTP 401/403 诊断保留状态码、服务域名及是否配置认证，不留 URL 查询参数、Token 或响应原文。失败状态及诊断随任务保留，停止盲目重复请求。该通用改进属于 Agent，**不计作旧 GeoDownloader 的 403 修复**。
5. 小范围真实下载另外复现了 Windows 长缓存路径下 `NamedTempFile.persist` 的 `os error 3`。共享瓦片的内容摘要路径超过传统长度后，原子提交失败。现在先规范化已存在的 blobs 父目录，再构造临时文件与提交目标，保持原子提交及内容校验，不缩短/混用不同图源的命名空间。
6. 任务事件契约同步生成。顺便补齐 TaskSpec/Plan 契约里原已实现但遗漏的可选 `pixelValueMode`，没有将其写成新增或额外验收的数值能力。
