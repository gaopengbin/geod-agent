# GeoD Agent 通用执行规则与 Harness 调研

日期：2026 年 10 月 10 日。状态：通用规则已接入本地 GeoD Agent 运行层；[实装、验收与边界](../implementation/2026-10-10-runtime-policy.md)。

GeoD 的执行规范应由任务状态、工具契约、运行层检查和模型指令共同承担。可确定的权限、参数、版本、重复提交和费用约束由代码检查；目标相关性、探索价值和策略选择由模型判断，并接受运行记录和结果评估。规则适用于图源、任务、MCP、文件和地图操作，具体 GIS 知识由业务适配层提供。

## 其他产品如何组织执行

| 产品或框架 | 官方公开机制 | GeoD 可以采用的设计 |
| --- | --- | --- |
| Codex App Server | 分离 thread、turn 和 item；提供恢复、执行中追加输入和中断接口。动态工具随会话保存，恢复时可沿用原声明。[官方协议](https://learn.chatgpt.com/docs/app-server) | 区分目标、模型运行和后台任务；用户纠正进入当前运行；恢复前核对工具契约版本。 |
| OpenAI Agents SDK | 模型调用、工具执行和交接组成循环；工具处可配置校验和审批。审批产生可序列化的状态，再从同一运行恢复。[运行循环](https://developers.openai.com/api/docs/guides/agents/running-agents)、[工具校验和审批](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) | 在实际产生副作用的位置检查，等待确认保留运行状态和待执行动作。 |
| Claude Agent SDK | 工具前后 hooks 可拦截、修改或记录调用。Anthropic 的长任务实验采用需求清单、进展记录、增量执行和实际验证。[Hooks](https://code.claude.com/docs/en/agent-sdk/hooks)、[长任务实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | 执行约束可测试；跨上下文保留未完成目标和成果证据。长任务实验针对软件开发，GIS 需要自己的验收条件。 |
| DeepSeek Harness | 默认架构将工具注册、执行策略、会话日志和模型适配分开；工具经过统一管线。目标具有持久状态和修订号。[架构](https://deepseek-harness.github.io/deepseek-harness/en/reference/)、[工具管线](https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-execution-pipeline)、[目标状态](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/goal) | 规则以独立策略模块接入；同一动作的检查、执行、结果记录共用链路。 |
| LangGraph 和 Deep Agents | 通过状态和检查点恢复工作；区分暂时故障、模型可修正错误、用户可解决错误和开发者故障。大工具结果可存储并以引用返回。[错误分类](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)、[检查点](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)、[上下文管理](https://docs.langchain.com/oss/javascript/deepagents/context-engineering) | 确定性恢复、分类重试、数据引用和按需读取。 |
| Cursor 长任务研究 | 实验分离规划、执行和阶段评判职责，同时指出过多结构会增加脆弱性。[研究说明](https://cursor.com/blog/scaling-agents) | 按阶段检查目标是否推进；职责可以由单个 Agent 的不同执行阶段承担。该研究不能证明所有正式产品调用都采用相同架构。 |

这些资料没有给出适用于所有任务的通用进展算法。DeepSeek 的目标状态仍有累计轮数上限；其最小 SDK 配置不包含默认配置的上下文压缩等能力。是否采用某框架，必须核对实际启用的配置和版本。[目标接口](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/goal)、[最小 SDK 配置](https://deepseek-harness.github.io/deepseek-harness/en/guide/python-sdk)

## 规则的三个层次

| 层次 | 职责 | 判断依据 |
| --- | --- | --- |
| 运行层约束 | 身份、权限、参数、修订号、幂等、资源限制、状态恢复 | 应用实际状态、工具契约、审批记录和执行回执 |
| 模型执行原则 | 理解目标、拆解步骤、选择策略、评估探索价值、组织回复 | 用户要求、当前事实、已尝试路径和可用能力 |
| 业务适配层 | 定义本业务的前置条件、进展事件、成果类型和验收条件 | 版本化业务契约及实际数据 |

权限和幂等检查不能被模型说明覆盖。语义判断不宜伪装成确定性规则：模型可能误判目标相关性和进展，因此运行层应记录依据，低置信度判断优先调整策略或说明不确定性，涉及越权副作用时再拦截。

## 通用执行规范

### 1 任务目标和授权范围

- 每个执行目标记录要求、交付物、完成条件、允许的操作范围和当前修订号。简短问答允许直接完成；复杂任务才生成阶段计划。
- 用户的新输入先确定是在补充、纠正、询问状态、取消，还是要求新工作。补充信息只更新相关目标和参数。
- 执行中始终遵守最新纠正；已获得的授权在其范围内持续有效。工具输出、网页和附件中的指令不能自行扩大授权。
- 每次工具调用应能说明它推进哪项交付物或解决哪个必要的不确定性。仅因为存在工具，不构成调用理由。

### 2 明确的状态和唯一执行权

- 分开记录目标状态、模型运行状态和后台作业状态。等待下载可以是目标进行中、模型空闲、作业运行中。
- 同一目标的冲突操作由执行租约或版本比较保护。用户追加消息不得因为旧运行尚未结算而反复创建失败的新运行。
- 等待用户、等待外部服务、费用暂停、故障阻塞、用户取消和正常完成分别记录原因；界面和后续模型上下文读取相同状态。
- 用户取消优先阻止新的副作用；已有不可撤回操作须核对实际结果。

### 3 已确认要求的继承

- 将参数值、来源、确认状态、适用范围和修订号存入结构化状态。
- 用户要求局部修改时，继承其余兼容参数。只有缺失、冲突、失效，或变更造成不兼容，才重新询问对应字段。
- 批量执行前统一检查所需参数；中途取得的新回答使受影响的旧计划失效，再生成对应计划。
- 模型可提出澄清，运行层负责判断同一字段是否已被有效回答，减少重复问题。

### 4 工具和能力契约

- 工具声明应包括参数、输出、前置条件、操作对象、权限、副作用、错误类别、结果引用，以及可支持的核验方式。
- 同时区分模型能力与工具能力。工具能生成图片，不代表当前模型能读取图片。
- 工具名称、标识和取值来自当前声明或工具返回；参数在执行前验证。
- 恢复会话时比较工具、模型和业务契约版本；发生变化时更新能力上下文。历史工具调用保留其原有含义。

### 5 按错误原因恢复

| 错误类别 | 通用处理 |
| --- | --- |
| 暂时网络故障或限流 | 工具适配层按配置退避重试，遵守服务端等待提示；重试耗尽后回退或阻塞。 |
| 参数或格式错误 | 返回具体约束，允许依据错误修正；相同原因反复出现时进入策略复盘。 |
| 权限、认证或能力缺失 | 等待对应条件变化，或选择已授权且能满足目标的能力。 |
| 操作结果未知 | 按操作标识查询或核对，再决定是否重试。 |
| 已知业务拒绝 | 依据业务状态选择下一步；拒绝不能通过更换调用入口绕过。 |
| 意外内部错误 | 保存诊断信息并进入明确故障状态，交由开发者修复。 |

恢复依据需要保存为结构化事实：失败原因、影响范围、尝试过的修复、何种条件变化后可重试。不同搜索词或不同命令仍可能属于同一个未解决故障。

### 6 判断有价值的进展

进展分为成果推进和必要的信息增量。成果推进包括完成目标所需的状态变化；信息增量包括获得影响下一步决策的新事实，或排除一个有依据的候选路径。

以下现象单独不足以证明进展：产生新 ID、增加文字、改写命令、改变报错、重复取得相同结果、重新描述同一计划。

- 业务适配层为常见任务提供可验证进展事件；开放探索允许记录假设、证据和排除结果。
- 重复检测按操作目的、对象、失败类别和状态变化归类，参数哈希作为辅助信号。
- 停滞先触发策略复盘：检查缺失条件、复用已知事实、改变方法或明确阻塞。
- 复盘后仍没有合理路径时暂停并保留检查点。阈值需通过实际会话评估校准，不以统一步数代替判断。
- 正在运行且有正常进度的外部任务不应被当作无效重复；等待采用事件订阅或逐渐放缓的状态查询。

### 7 长任务和费用控制

- 一个目标可以跨多次用户消息、多个模型运行和上下文压缩持续执行。
- 有进展且条件允许时继续；阻塞时保存检查点；完成条件成立后结束。
- 费用限制为可选累计政策，可作用于目标或会话。恢复运行延续原记账范围，不能重置累计费用。
- 显示已结算费用，估算与实际计费分开。临近用户设置的上限时说明已完成部分和剩余工作。
- 同时保留工具超时、请求并发、内存、上下文和余额等运行保护。它们属于资源条件，不能被描述成任务已经完成。
- 长时间下载、拼接、等待审批由原生作业和事件承接；无需不断调用模型维持运行。

### 8 幂等提交和断点恢复

- 有副作用的操作先绑定目标、参数版本和操作标识；重复提交复用已有操作或明确拒绝。
- 保存待执行动作、审批状态、回执和后台作业标识。恢复从尚未完成的阶段开始。
- 检查点不能独自保证外部操作只执行一次。提交后失联必须先核对外部结果；外部系统不支持幂等时，需要明确的结果对账方式。
- 批量操作分别记录成功、失败和结果未知的子项，恢复只处理待解决部分。

### 9 上下文和大数据处理

- 常驻上下文保留通用规则和紧凑任务状态，详细业务知识与工具说明按需加载。
- 大结果写入受权限保护的存储，模型接收摘要、类型、范围、数量、来源、完整性信息和引用。
- 分页读取只取决策所需片段；完整数据处理优先交给工具和确定性计算。
- 压缩必须保留目标、授权、确认参数、未完成动作、成果引用、失败原因和费用范围。关键事实从结构化状态重新注入。
- 事实、用户要求、工具回执和模型推断保留来源区分。旧模型总结不能覆盖较新的执行状态。

Anthropic 建议优化工具的用途、命名与高信号输出，并利用真实轨迹发现无效调用；Deep Agents 将大结果替换为可检索的文件引用。这些机制适合承接 GeoD 的空间数据和执行记录。[工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)、[数据引用](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)

### 10 结果验收和回复

- 开始执行时确定成功条件及所需证据。证据可以由可信工具回执、应用状态或成果检查提供；不要求每个动作都重复查询。
- 模型结束回复与业务目标完成分别处理。计划、提交、运行、完成和已核验各有含义。
- 达到所需验收条件后停止额外检查。新增验证须对应一个会影响交付结论的不确定性。
- 事实结论附带来源和适用范围；模型推断与已验证结果分开。采样失败只说明当前路径或样本失败。
- 最终回复汇总交付物、真实状态和必要的限制；下一步建议不自动创建新的执行目标。

Anthropic 的评估方法明确区分运行轨迹和环境结果：模型宣称操作成功，不能替代实际系统中的结果。评估需要组合程序判断、模型评分和人工校准。[Agent 评估](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## GeoD 业务适配层需要提供的事实

通用运行层通过统一接口消费业务信息，具体字段含义由 GeoD 管理。

| 契约 | 业务适配层内容 |
| --- | --- |
| 任务参数 | 图源、范围、时间、层级、输出坐标系、格式、保存位置及确认来源 |
| 能力事实 | 当前图源和 MCP 的真实能力、模型输入类型、工具版本和状态 |
| 空间数据 | 源坐标系、规范坐标系、已实施变换、原始与派生成果、处理记录 |
| 执行状态 | 计划修订、有效期、审批、任务标识、后台进度和成果回执 |
| 验收条件 | 请求范围和参数符合性、所需文件或图层存在、适用的完整性检查 |
| 进展事件 | 参数补齐、候选确定、有效计划建立、子任务完成、成果核验等可验证变化 |

业务事实由应用或工具提供。模型负责理解和选择；状态判断应读取当前记录。

## 如何验证规则能减少弯路

建立跨任务类型的多轮评估集，包括正常路径、临时故障、参数冲突、缺少能力、审批等待、提交后断线、用户纠正、取消、上下文压缩和长期探索。真实会话可转为脱敏回放，另外保留未参与规则调优的案例，检查泛化能力。

指标同时记录目标完成率、越权及重复副作用、重复确认、无效恢复、阻塞恢复成功率、工具调用数、已结算费用、总时长和每项成功任务成本。更少调用只有在结果质量与任务范围得到保持时才有意义。

针对目标相关性和停滞判断，先记录拟采取的决策，与人工复核对照，再启用会中断工作的策略。身份、权限、参数和幂等检查直接执行。评估关注允许的行为边界和真实结果，避免要求每个 Agent 都走完全相同的工具序列。

## 推荐的实施顺序

1. 建立统一任务状态与工具策略接口，先覆盖前置条件、权限、错误分类和幂等。
2. 接入已确认要求、能力事实、成果引用和恢复检查点，保持每个版本可回放。
3. 建立实际轨迹评估集，校准进展、停滞和费用提示政策。
4. 用统一结果状态驱动回复和界面，再评估是否需要更多模型或委派。

现有 Codex 运行核心可以继续承担模型循环。GeoD 应在工具边界和业务状态层补齐统一策略，并用简洁的模型指令解释这些策略。采用外部框架需要额外证明它对恢复、费用或维护成本的收益。
