# GeoD Agent 整体 UI 调研与第二版规范建议

调研日期：2026-10-01。范围：公开的官方设计规范、官方产品文档、开源仓库，以及当前 GeoD 前端代码和已有界面复现截图。

## 1. 推荐结论

**用 Codex 的会话方式和 VS Code 的工作台结构组织产品，以 Fluent 2 / Ant Design X 的设计规则补齐一致性，保留 GeoD 现有蓝色品牌、React 组件和 Motion。**

本次查到的是各公司的设计体系和 AI 交互指导，没有找到一个要求所有 Agent 软件采用相同布局的通用 GUI 标准。产品样例、组件库、运行协议和可访问性标准应分别使用。

GeoD 同时包含自然语言操作、地图、数据与长时间后台任务，适合「会话 + 工作画布 + 任务检查区」。一张大聊天页面无法承载所有领域操作；四个区域始终等量展开也会造成拥挤。区域的显示应随当前工作变化，且让用户随时展开、收起和拖动。

### 我们应当形成的产品规则

- 聊天记录保存意图、简短结果和对应对象的入口。
- 详细计划、地图、批量操作和成果查看在工作区域承载。
- 界面的 loading、按钮是否可用、任务是否运行，直接由系统状态驱动。
- AI 回复由模型根据实际工具结果生成。任务进度不能靠修改回答文字维持。
- 一次操作在多个视图里可以有入口，但详细内容只在一个位置展示。

以上是针对 GeoD 的综合建议，不是任何一家原规范的全文或强制要求。

## 4. 可以复用什么

| 项目 | 本次验证 | 推荐方式 |
| --- | --- | --- |
| [assistant-ui](https://github.com/assistant-ui/assistant-ui) | React / TypeScript；主仓库 MIT；[工具组](https://www.assistant-ui.com/elements/tool-group)和[思考展开](https://www.assistant-ui.com/elements/reasoning)有独立组件文档 | 优先研究折叠、流式文本与滚动行为；补缺失组件时按需适配。保留当前 Codex 事件与 GeoD 状态库 |
| [Ant Design X ThoughtChain](https://x.ant.design/components/thought-chain/) | 可控展开；loading / success / error / abort 状态；面向 Agent actions/tools | 参考执行时间线及状态映射，不为一个组件导入整套 Ant Design 主题 |
| [Carbon AI Chat](https://github.com/carbon-design-system/carbon-ai-chat) | Apache-2.0；React 和 Web Component；[官方文档](https://chat.carbondesignsystem.com/tag/latest/docs/documents/Overview.html)支持嵌入容器、流式消息和主题定制 | 可作为完整聊天框架候选，但替换当前整套对话会增加适配工作，暂不优先 |

组件包版本、依赖体积、授权文件和键盘行为应在实际采用时再核对。本次没有添加 npm 依赖。已有项目先沿用现有组件，补充组件再检查 beUI 与上述项目是否适合。

### 不要把协议当成 UI 规范

[AG-UI](https://docs.ag-ui.com/introduction)规定 Agent 与前端之间的事件和状态流；同一官方页面区分 A2UI 的生成式 UI 描述用途。它们不规定 GeoD 的字体、栏宽、卡片高度或按钮外观。当前 Codex app-server 已提供事件通道，单纯优化 UI 不需要额外换一套运行协议。

## 5. 对照当前 GeoD 的审查

证据是本次读取的代码与已有复现图。本次没有重新操作用户桌面或完整测试真实会话；复现截图包含演示数据，不代表当前下载状态。

### 已经可以继续沿用

- `chat-work` / `codex-work.css` 已有整轮归组与紧凑时间线。
- `transcript-plan-card` 已把单任务入口压到 44px，多任务组合并为 60px；详情集中到右侧。
- `task-queue-view` 已支持多任务、多选、待处理/已结束以及不同状态动作。

- `resizable-workspace` 已支持拖动、键盘方向键和宽度保存。

不能把先前已经修复的问题继续列为未实现。下一版需要把这些局部成果统一起来。

### 仍需系统优化的地方

| 优先级 | 位置与依据 | 用户影响 | 下一版建议 |
| --- | --- | --- | --- |
| P1 | `resizable-workspace.tsx` 在宽度小于最小宽度总和时仍按比例压缩各栏；`workspace.css` 在 951px 开始四栏桌面布局 | 字号不变但可读宽度不足，对话和地图互相挤压 | 按内容可用宽度切换区域，保留拖动；不要只不断缩窄四栏 |
| P1 | `styles.css`、`theme.css`、`workspace.css` 多处定义相同容器尺寸和基础外观 | 修改需要依赖覆盖顺序，区域尺度容易漂移 | 统一设计变量、基础组件和页面布局三层；保留最终有效样式，再逐步清理旧声明 |
| P1 | 任务复现图中列表与选中任务同时完整展开；选中任务有摘要、事实、路径、确认区、详情 | 多任务时检查区层级重、标题和元数据重复 | 顶部队列，下面只显示选中项的必要信息；更多参数、记录、路径按需展开 |
| P2 | 连接器复现图中「查看用法」在卡片网格后插入全宽说明 | 打开说明会把后续网格推移，阅读焦点不稳定 | 宽屏在页内侧栏显示说明；窄屏用页内详情视图，保留返回和原滚动位置 |
| P2 | 多个样式文件直接写颜色与局部尺寸；已有主题变量与 Tailwind 变量两种入口 | 深浅主题和禁用、选中、警告状态难以统一复核 | 建立状态颜色及 foreground/background 配对表，组件使用同一来源 |

## 6. GeoD 第二版工作台布局

```mermaid
flowchart LR
    Nav[导航与会话列表] --- Chat[对话与输入]
    Chat --- Canvas[地图 / 数据 / 成果画布]
    Canvas --- Inspector[任务列表与选中对象详情]
```

四个区域仍可拖动；下面的数值是 GeoD 原型建议，不是行业标准。

| 可用宽度 | 默认布局 | 交互 |
| --- | --- | --- |
| ≥ 1440px | 导航约 200px；对话约 400px；任务区约 320px；其余给画布 | 可同时查看四区；检查区可收起，画布随之扩展 |
| 1120–1439px | 导航、对话、画布三栏 | 任务详情按需在画布侧展开；继续保留对话宽度和原会话位置 |
| 900–1119px | 导航可压为图标栏；对话与画布并排 | 任务/数据检查视图占用工作区域，提供明确返回入口 |
| < 900px | 当前会话与工作视图切换 | 一个主视图可读，后台任务入口常在；切换不打断工作 |

布局由当前内容、缩放比例与用户保存宽度共同决定；实现时要测 100% / 125% / 150% 系统缩放。

### 各区的职责

**导航**：新对话、图源、技能与连接器、工作区和会话。工作区操作留在分组菜单；导航页不会改写其他会话的工作区。

**对话**：用户输入 → 一条本轮执行摘要 → 模型最终回复 → 紧凑对象入口。已结束的整轮执行默认收起；用户可展开。批量任务只显示一个固定高度入口。

**工作画布**：地图、数据表或成果预览。地图保持整洁；图层管理和对象动作放在画布边缘可展开区域。图源署名等实际数据展示要求按数据层处理，不随意删掉。

**任务检查区**：任务 / 成果 / 数据三个对象视图；任务队列与单个任务详情分层。任务列表有明确名称、状态和短进度；详情只保留本次决策所需参数与动作。路径、哈希、工具原始输出放在可展开详情中。

**图源、连接器与设置**：统一页内页面骨架——标题和主动作、搜索/分类、紧凑网格或列表、选中对象的页内详情。凭据输入等短暂操作仍可使用小对话框。

## 7. 第二版组件规则草案

### 视觉与密度

- 保留蓝色品牌。主背景、导航、画布与浮层使用少量语义层级，减少每块都套彩色卡片的情况。
- 间距变量使用 4 / 8 / 12 / 16 / 24px；同级行高、标题高度和内边距统一。
- 常用字号保持现有 14px 可读基线；正文与标题用字号、字重和间距表达层级，减少英文大字标签。
- 面板标题约 44px；普通操作行约 32–36px；单任务入口 44px；多任务入口 60px。它们是项目目标值。
- 按钮分主动作、次动作、图标动作；图标入口有中文提示和键盘焦点。颜色同时配对检查文字、底色、边框、悬浮与禁用状态。
- 正常正文及可用按钮文字按 WCAG AA 的 4.5:1 核对；大号文字另有 3:1 条件，禁用组件文字为规范例外，但产品仍应尽量清楚。[W3C Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

### 动效保留并统一

[Fluent Motion](https://fluent2.microsoft.design/motion)用动效表达状态和区域关系，并要求时间与移动尺度匹配。GeoD 应保留用户要求的等待、工具调用、流式输出和消息滚动动效。

| 场景 | GeoD 建议 |
| --- | --- |
| 思考 / 工具运行 | 状态图标和文字有连续动态反馈；收到首个内容后进入实际流式状态 |
| 执行区展开/收起 | 约 200–260ms；完成后收起整轮，保留手动展开能力 |
| 任务/对象出现 | 约 180–220ms；只让新增内容进入，不重新播放历史记录 |
| 工作区面板开合 | 约 220–300ms；拖动时立即跟随，不叠加拖拽延迟 |
| 消息滚动 | 底部时跟随流；用户上翻或展开记录后停留原位置，显示回到底部入口 |
| 行悬浮 | 背景、边框和文字状态变化；不缩放、不抬高、不改变行高 |
| 后台进度 | 原生任务状态更新进度条；完成/失败时一次提示，不把每次轮询写入聊天 |

上述时间是原型起点，需要本机体验调节。尊重用户显式选择的减少动态效果设置，同时保证加载和状态变化仍然可识别。

### 状态与作用域

- 区分：准备会话、等待模型、流式生成、工具运行、等待用户输入、模型轮次完成、后台任务运行。
- 「停止回复」作用于当前模型轮次；「取消下载」作用于具体下载任务，两个动作不混用。
- 完全访问权限按现有授权执行；逐次确认才出现确认动作。不为研究规范额外添加授权/协议流程。
- 任务、图层、数据连接、成果和工具记录带会话/对象归属，选中项保持稳定。
- 上下文入口保持小圆环；弹出详情使用 K，显示实际可用窗口及计量来源。
- 拖动条支持键盘和可读名称。当前已有部分实现，后续对照 [W3C Window Splitter](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/)补齐控件关系与收起/恢复；该 APG 模式页自身注明仍在完善，不能据此声称完整合规。

## 8. 建议实施顺序与验收

1. **工作台与设计变量**：统一页面骨架、可用宽度策略和语义颜色；先用已有实际组件做整页预览。
2. **会话和任务对象**：整轮执行、对象入口、队列与详情形成统一层级，保留现有归属和权限逻辑。
3. **管理页面与数据工作区**：图源、连接器、数据库、文件输入共用页内结构，统一错误和等待反馈。
4. **完整流程验收**：真实模型读 PostGIS/文件范围 → 生成多个计划 → 后台下载 → 地图加载成果。界面演示数据和真实任务证据分别标明。

必须覆盖：浅/暗主题；窄/宽窗口；1/8/32 项任务；长名称和路径；工作中补充指令；停回复但保留后台任务；切会话隔离；网络断开与恢复；上翻阅读时不被滚动抢走；键盘操作。真实操作需以任务账本和实际文件为准。

开发阶段使用本地热更新预览。完成一组连贯的整页改动后再做真实流程验收，避免每改一个按钮就安装一遍。
